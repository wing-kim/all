# XR 자동 시험

헤드리스 Chrome(맥에 설치된 Google Chrome)과 IWER(Quest 3 에뮬레이터)로 XR 기능을 점검합니다. 실기기 확인을 대신하지는 않습니다.

```bash
# 작업 폴더(wing-kim/all 체크아웃) 루트에서 정적 서버
python3 -m http.server 8790 --bind 127.0.0.1
# 다른 터미널
cd xr/tests && npm install
node smoke.mjs --shots   # 기능 26항목 + 그리기 호출 기준(< 200), 화면은 out/
node compat.mjs          # 원본과 화면 동일(Q2), 대체 경로(Q14), 반복 진입 메모리(Q13)
node ux.mjs              # 사용감 시나리오(실제 자세와 버튼으로만 조작), 화면은 out/ux-*.png
node mp.mjs              # 멀티플레이 28항목(브라우저 4개를 실제 공개 중계망으로 연결, 인터넷 필요)
npm run check            # 네 가지 모두
```

- `fallback.html?mode=nobridge|noxr`: Wing 이 연결 통로 줄 없이 올린 경우를 흉내 냅니다.
- `diag.mjs`, `shot.mjs`: 개발용 진단과 화면 캡처.
- Wing 의 새 업로드를 합친 뒤에는 두 시험을 모두 돌리고 결과를 계획서 14장에 남깁니다.

## 자체 검토 체계

기능이 동작하는지(smoke)와 사람이 실제로 쓸 수 있는지(ux)를 나눠 봅니다. 고칠 때마다 아래 순서를 지킵니다.

1. **재현 먼저**: 실기기에서 나온 문제는 `ux.mjs`에 같은 자세와 입력으로 실패하는 시나리오를 먼저 만들고, 실패를 확인한 뒤 고칩니다(예: 순간이동 뒤 메뉴 레이, 피규어 범위 밖 손 막대, 도로 착지 불가).
2. **실제 입력만**: 시나리오는 내부 함수 대신 컨트롤러 위치·방향, 트리거, 스틱, 머리 방향으로 조작합니다. 그래야 판정 거리, 자르기, 가림 같은 문제가 드러납니다.
3. **눈으로 보기**: `ux-*.png`는 웹 패널을 숨긴 사용자 눈높이 화면입니다. 메뉴, 피규어 경계, 계단, 램프 화면을 매번 직접 열어 확인합니다.
4. **예산**: 그리기 호출은 한 프레임에 여러 번 그리는 패스(가상 방, 손·메뉴)를 모두 합산해 200회 미만을 봅니다.
5. **실기기**: 퀘스트를 USB로 연결하면 Meta 개발 도구(MCP의 화면 캡처·logcat·성능 추적)로 같은 장면을 확인합니다. 이 맥에는 아직 `adb`가 없어 Meta Quest Developer Hub 또는 Android platform-tools 설치가 필요합니다.
